# 19 · Architecture Audit V2

**Method:** the architecture was **measured**, not read. Dependency graphs,
cycle detection, layering analysis, fan-in/fan-out, and hot-path benchmarks were
generated by executing tooling against the tree. Every number below is
reproducible.

**Scope:** 87 non-test modules, 16,758 lines, 489 tests.

---

## 1 · Executive Summary

This is a **well-architected system with three specific, addressable weaknesses**
and one genuinely excellent property that most codebases of this kind never
achieve.

The excellent property, measured:

```
React / React Native imports in domain layers
  learning      0 of 13 files
  progression   0 of  7 files
  generators    0 of 14 files
  curriculum    0 of  2 files
  i18n          0 of  2 files
```

**The entire learning engine — mastery, scheduling, diagnosis, progression,
content generation — is framework-independent.** It is plain TypeScript over
plain data. That is why 489 tests run in 24 seconds with no renderer, why the
economy could be simulated adversarially before it was wired to anything, and
why the UI was replaced twice without touching the learning logic. Almost every
other strength in this report is downstream of that one decision.

The second measured strength:

```
circular dependencies:      0   (across 87 modules)
upward layering violations: 6   (all shallow, all type-level or data-level)
```

Zero cycles in a codebase this size is not luck; it reflects a real dependency
discipline. The three weaknesses are:

| # | Weakness | Severity | Fix cost |
|---|---|---|---|
| W1 | `GameContext` is a 55-member god object | **High** | 1 wk |
| W2 | `estimateAll` is O(skills × log) — 98 ms at 10× content | **High** | 2 d |
| W3 | Language is binary and branched in 68 places outside i18n | **Medium** | 1 wk |

None is structural. None requires a redesign. All three are contained.

## 3 · Domain Architecture Review

### Measured layer dependency matrix (top edges)

```
 15  components -> theme         10  progression -> learning
 14  app -> hooks                 6  context -> learning
 14  app -> components            5  learning -> generators
 13  app -> context               5  learning -> i18n
 13  app -> learning              4  progression -> generators
 12  app -> i18n                  3  generators -> learning
```

The shape is correct: dependencies flow from UI toward domain, and domain
toward pure data. `app` is the only layer with broad fan-out, which is what a
presentation layer is *for*.

### Domain-by-domain

| Domain | Module | Verdict |
|---|---|---|
| **Skills** | `learning/skills.ts` | **Excellent.** A 45-node prerequisite DAG is the correct model and it is the spine everything else hangs from. Fan-in 21 — the second most depended-upon module in the system, appropriately. |
| **Mastery** | `learning/mastery.ts` | **Excellent design, one performance flaw (W2).** Derived-never-stored is exactly right: the estimate can be recomputed after any change to the estimator, so there is no migration risk and no drift. |
| **Diagnostics** | `learning/misconceptions.ts` | **Good, but the largest file at 734 lines.** Detection logic and content are interleaved. Coverage is complete (45/45 skills). |
| **Scheduling** | `learning/scheduler.ts` | **Good.** Pure function from (class, estimates, now) to a plan. Recently hardened against three scale bugs. |
| **Progression** | `progression/*` | **Excellent.** Cleanly separated into formula (`xp`), countermeasures (`antiGrind`), curves (`levels`), orchestration (`award`). The `award` module exists precisely so no screen has to assemble the economy — good instinct. |
| **Content** | `generators/*` | **Adequate, and the weakest domain.** See §5. |
| **Curriculum** | `curriculum/*` | **Good.** Board model and chapter graph are data, and the chapter graph is a *view* over the skill DAG rather than a parallel structure. |
| **Statistics** | scattered | **Under-modelled.** Derived views live in `attempts.ts`, `feedback.ts`, `parentReport.ts` and inline in screens. No single statistics domain. Low severity today; will bite when a teacher mode needs the same aggregations. |
| **Achievements** | `progression/achievements.ts` | **Good.** Each achievement is a pure predicate over (log, estimates). Trivially testable, and the anti-farming property is asserted directly. |
| **Parents** | `learning/parentReport.ts` | **Good.** One composer over existing data, no new model. |
| **Session state** | `context/GameContext.tsx` | **The one genuine problem.** See W1. |

## 4 · Module-by-Module: the three weaknesses

### W1 · `GameContext` is a god object — **High**

Measured: **55 exported members** in one context, 882 lines, fan-in 14.

```
selectedClass selectedCategory difficulty sessionType selectedTable score
questions currentIndex isGameOver totalQuestions wrongAnswers isTablesMode
startGame startTablesGame submitAnswer nextQuestion endGame highScores
progressStats tablesBest savedMistakes saveScore saveProgressStats
clearMistake loadAll getHighScore attempts mastery streak answeredToday
startAdaptiveSession isAdaptive recordAttempt rootGapFor sessionSkillFor
retargetNext topMisconceptions totalXp level masteryIdx masteryLabel
lastAward board setBoard lang setLang prefsLoaded timerPref setTimerPref timerOn
```

At least five distinct responsibilities are fused:

1. **Session state** — questions, index, score, wrong answers
2. **Persistence** — 15 storage keys, load/save/migrate
3. **Learning** — attempts, mastery, scheduling, retargeting
4. **Progression** — XP, ledger, level, awards
5. **Preferences** — board, language, timer

Three concrete consequences, not stylistic objections:

- **Every consumer re-renders on every change.** A component that only needs
  `lang` re-renders when `score` increments — 14 modules depend on this context.
- **`recordAttempt` is where bugs concentrate.** The XP double-count bug
  (updater re-invocation) and the stale-closure risk both arose here, because
  one function mutates the log, derives mastery, prices XP, updates the ledger
  and schedules persistence.
- **It cannot be tested without React.** It is the *only* significant piece of
  domain-adjacent logic in the system with that property, which is why it has
  no direct tests while `learning/` has ~200.

**Recommendation: split into four contexts** — `SessionContext`,
`LearnerContext` (attempts + mastery, read-mostly), `ProgressionContext`,
`PreferencesContext`. Domain logic moves to a plain `recordAnswer(state, event)`
reducer that is unit-testable without a renderer. This is ~1 week and is the
single highest-value refactor available.

### W2 · `estimateAll` is O(skills × log) — **High**

Measured, by executing the real function:

```
estimateAll cost as the curriculum grows
   45 skills ×  4,000 rows  =    4.6 ms    (today)
  150 skills ×  4,000 rows  =    8.7 ms
  450 skills ×  4,000 rows  =   22.7 ms
  450 skills × 20,000 rows  =   98.3 ms    <- 10x content: a dropped frame
```

`estimateMastery` filters the **entire log** once per skill. Today, at 45 skills
and a 4,000-row cap, this is 0.76 ms and invisible. At the 10× content growth
the brief asks about, it becomes ~98 ms on **every answer** — a visible stall in
the feedback loop, on the low-end Android hardware this product targets.

The fix is a single-pass bucket, and I measured it:

```
 450 skills × 20,000 rows:  filter-per-skill 121.3 ms  ->  bucketed 0.5 ms   (258x)
```

**Two days of work, 258× headroom, no API change.** This is the clearest
cost/benefit item in the report.

### W3 · Language is binary and leaks — **Medium**

Measured: `export type Lang = 'en' | 'hi'`, 174 string pairs, and **68
`lang === 'hi' ? … : …` ternaries outside the i18n layer**, in 22 files —
including inside question generators:

```ts
text: lang === 'hi' ? `${a} + ${b} लगभग कितना है?` : `About how much is ${a} + ${b}?`
```

Adding Marathi, Tamil or Bengali — plausible for this market — means editing 68
call sites and every `{ en, hi }` record. The i18n *layer* is well designed; the
problem is that callers bypass it with inline ternaries.

**Recommendation:** make `Lang` an open string type, convert `{ en, hi }` pairs
to `Record<Lang, string>` with an English fallback, and replace inline ternaries
with `t()` / `pick(record, lang)`. Mechanical, ~1 week, and it converts "add a
language" from a refactor into a data change.

## 5 · Content Architecture — the strategic question

**Content is executable TypeScript, not data.** 2,734 lines of generators, no
`content/` directory, no schema.

This has served the product extremely well so far. Generated content gives
infinite non-repeating questions, guaranteed answer correctness (the generator
*knows* the answer), and property-testability across 27,000 samples. Those are
real advantages and I would not throw them away.

But it has three consequences worth naming honestly:

1. **A non-programmer cannot author content.** Every new question type is a
   pull request. This is the binding constraint on curriculum growth, not
   performance.
2. **Content ships with the app.** No content updates without a store release.
3. **AI-assisted content generation (a stated future goal) has nowhere to put
   its output.** There is no content schema for a model to target.

**Recommendation — a hybrid, not a rewrite.** Introduce a declarative
`QuestionTemplate` schema (parameters, constraints, answer expression,
distractor strategy, localised text keys) and a small interpreter. Migrate new
content to templates; leave existing generators in place behind the same
`Question` interface. Generated and authored content coexist because they
already produce the same type.

Extensibility for the other axes is genuinely good and I want to say so plainly:

| Adding… | Cost | Verdict |
|---|---|---|
| A question **type** | 3 switch sites (`interactions`, `AnswerSurface`, `award`) | **Excellent** — the discriminated union is doing real work |
| A **skill** | 1 entry + `resolveSkill` case | **Excellent** |
| A **chapter** | 1 data entry | **Excellent** |
| A **board** | 1 config + availability table | **Good** |
| A **language** | 68 call sites | **Poor** (W3) |
| A **question generator by a non-coder** | impossible | **Poor** (§5) |

## 6 · Boundaries and Dependency Analysis

**Circular dependencies: 0.** This is the headline. In a codebase with 87
modules and a domain this interconnected, zero cycles indicates deliberate
discipline.

**Upward violations: 6**, and all are defensible:

```
generators -> learning   (3)  arithmetic.ts, reasoning.ts need skill ids
                              and the misconception library to build
                              diagnostic distractors
curriculum -> learning   (2)  chapters.ts names skill ids
lib -> generators        (1)  progressApi types
```

These are *type and identifier* dependencies, not behavioural coupling. They
exist because `SkillId` and the misconception catalogue are genuinely shared
vocabulary. The clean fix is a tiny `domain/ids.ts` holding `SkillId`,
`MisconceptionId` and the catalogue, which both layers import downward — but
this is cosmetic, and I would not prioritise it.

**Highest fan-in** (correctly, these are the vocabulary modules):

```
25  generators/types.ts     21  learning/skills.ts     17  theme/useTheme.tsx
24  i18n/strings.ts         17  constants/colors.ts    14  context/GameContext.tsx
```

`constants/colors.ts` at 17 is a **shim scheduled for deletion** — it maps the
legacy palette onto the new tokens. It should not survive the UI migration.

## 7 · Data Model

**Strong.** The append-only attempt log as single source of truth is the right
decision, and it is the reason mastery, statistics, achievements and the parent
report can all be added without a migration.

Measured storage profile:

```
attempt log at 4,000-row cap:  1,094 KB JSON
  JSON.parse                     5.3 ms   (startup, blocking)
  JSON.stringify                 4.2 ms   (debounced off the answer path)
```

**Three real risks:**

- **R1 · 15 storage keys, 1 versioned.** Only `attempts` has a schema version.
  `xp_ledger`, `total_xp`, `theme`, `timer_pref` and the four `v2_*` keys have
  none. A future change to the ledger shape has no migration path.
  **Fix: one `@mw/schema` manifest versioning every key.** Half a day.
- **R2 · The 4,000-row cap is a silent data loss boundary.** At ~50
  questions/day that is eight months; a committed learner loses their earliest
  history with no notice. Acceptable today, but the *decision* should be
  explicit and the eviction should preserve per-skill summaries.
- **R3 · No device identity beyond a generated UUID.** Fine for offline-first;
  becomes the blocker for optional cloud sync.

## 8 · Performance Architecture

Measured on the real hot path:

```
--- 4,000-row log ---
  estimateAll             0.76 ms    (every answer + every derived render)
  scheduleSkills          0.11 ms
  buildSession(10)        0.17 ms
  evaluateAchievements    5.37 ms    <- worth watching
  buildParentReport       2.61 ms
```

**Today: healthy.** Nothing on the answer path exceeds a frame budget.

**Two future bottlenecks**, both measured:

1. **`estimateAll` at 10× content — 98 ms** (W2). Fix costs 2 days, buys 258×.
2. **`evaluateAchievements` at 5.4 ms** and growing with both log length *and*
   achievement count. It runs 14 predicates, several of which sort the whole
   log. Should be computed on session end and cached, not per render.

**Startup** is dominated by the 5.3 ms parse — fine, but it will grow linearly
with the cap. If the cap rises, move parsing off the main thread or store a
rolling summary alongside the log.

## 9 · Testing Architecture

**The strongest dimension, and it is a direct consequence of the pure-domain
decision.**

```
learning      11 files, ~200 tests        theme          2 files, ~27 tests
progression    2 files,  ~43 tests        hooks          1 file,  ~34 tests
generators     3 files,  ~60 tests        i18n           1 file,  ~38 tests
curriculum     2 files,  ~42 tests        app/components 0 files    <-- gap
```

What the architecture makes possible, and which most RN codebases cannot do:

- **Simulation.** The XP economy was run against seven adversarial strategies
  over 30 simulated days *before* it was wired to a screen.
- **Property testing.** 27,000 generated questions checked for invariants.
- **Benchmarking.** This audit's numbers were produced by importing production
  modules directly — no mocks, no harness.

**The gap: zero UI tests across 14 screens.** Three of the most damaging bugs
found in recent work — the light-on-dark tile mismatch, the unreadable praise
line, the unlocalised difficulty screen — were all invisible to 489 unit tests
and were caught only by driving a browser by hand. That should be automated.

## 10 · Future Growth Assessment

| Requirement | Ready? | Blocker |
|---|---|---|
| **10× content** | ⚠️ | W2 (98 ms) and §5 (content is code) |
| **100× learners** | ✅ | Fully offline; no shared state to scale |
| **Additional curricula** | ✅ | Board model is data |
| **Additional languages** | ❌ | W3 — 68 branch sites |
| **Optional cloud sync** | ✅ | Append-only log with union merge is *ideal* for sync — commutative, conflict-free by construction |
| **Teacher mode** | ⚠️ | Needs a statistics domain (§3) and multi-learner identity |
| **AI-assisted content** | ❌ | No content schema to target (§5) |

The cloud-sync answer deserves emphasis: `mergeAttempts` is already a
union-by-identity over immutable facts. That is a CRDT in all but name, and it
means sync can be added without touching the data model — an unusually good
position to be in.

## 12 · Top improvements, in priority order

**Do now (2 weeks, high confidence):**

1. Bucket the attempt log once in `estimateAll` — 258× headroom, 2 days.
2. Split `GameContext` into four contexts; extract `recordAnswer` as a pure
   reducer — 1 week.
3. Add UI smoke tests for the practice loop and home at three viewports —
   automate what is currently manual browser checking.
4. Version every storage key under one manifest — half a day.

**Do next (3 weeks):**

5. Open the `Lang` type; replace 68 inline ternaries with lookups.
6. Cache `evaluateAchievements` at session end rather than per render.
7. Delete `constants/colors.ts` once the UI migration completes.
8. Extract a `statistics/` domain from the four places aggregations now live.
9. Split `misconceptions.ts` into detection logic and a content catalogue.

**Do when the need is real (not before):**

10. `QuestionTemplate` schema and interpreter, alongside existing generators.
11. Multi-learner identity — only when teacher mode is actually committed to.
12. Move log parsing off the main thread — only if the cap rises above ~10k.

I deliberately do **not** recommend: a state-management library (the reducer
split solves the real problem), a monorepo package split (87 modules does not
warrant it), an event bus (would add indirection without removing coupling), or
a repository/ORM layer (AsyncStorage behind a thin typed façade is proportionate).

## 13 · Final Verdict

**8.0 / 10 — ready for the next five years, with two weeks of targeted work.**

This architecture earns a high score for one reason above all: **the domain is
pure**. 38 modules of learning, progression and content logic with zero
framework dependencies, zero circular dependencies, and ~200 unit tests that run
without a renderer. That property is what has allowed the product to absorb an
adaptive scheduler, a diagnostic engine, an XP economy, a visual layer and two
UI rewrites without the architecture bending.

The three weaknesses are all *contained* and none requires redesign:

- The god object is a **composition** problem — split the context, extract a
  reducer.
- The O(S×N) hot path is a **data-structure** problem — one bucket, 2 days.
- Binary language is a **type** problem — open the union, replace ternaries.

The strategic question, which is not urgent but should be decided
deliberately rather than by default, is **content-as-code**. It is currently a
strength (correctness by construction, infinite variation, property-testable)
and will become the binding constraint on curriculum growth and on any
AI-assisted authoring. The hybrid path preserves the strength while removing the
ceiling.

**What I would not change:** the append-only attempt log, derived-never-stored
mastery, the skill DAG, the `Interaction` discriminated union, the separation of
XP formula from anti-grind countermeasures, and the pure-function scheduler.
Those are correct and should be defended.

### Reproducing this audit

```bash
cd artifacts/mobile
npx vitest run                      # 489 passed
npx tsc -p tsconfig.json --noEmit   # clean
```

Dependency graph, cycle detection, layering analysis and hot-path benchmarks
were produced by scripts that import production modules directly. They should be
promoted to CI checks — an architecture regression (a new cycle, a new upward
edge, a hot path crossing a frame budget) should fail the build rather than wait
for the next audit.

**Caveat:** this audit measures structure, dependencies and performance. It does
not measure whether the *product* teaches children mathematics — that remains
unvalidated, as docs/13–18 repeatedly note, and no architectural score should be
read as evidence about learning outcomes.
